## Нужен ли `await` при закрытии скоупа, если нет `Disposable`-сервисов?

Да. Всегда используйте `await` с `CherryPick.closeRootScope()`, `CherryPick.closeScope()` и
`scope.dispose()`, даже если сейчас ни один сервис не реализует `Disposable`. Если позже вы
добавите очистку ресурсов, реализовав `dispose()`, CherryPick обработает её автоматически, и
код завершения менять не придётся.

:::tip
[`cherrypick_lint`](/ru/linting/) подсвечивает пропущенный `await` на закрытии скоупа прямо в IDE.
:::

## Когда использовать `tryResolve` вместо `resolve`?

`tryResolve<T>()` / `tryResolveAsync<T>()` нужны, когда отсутствие биндинга — ожидаемая
ситуация: они возвращают `null`, если ничего не зарегистрировано. `null` означает
«не зарегистрировано», а не «ошибка» — неверный запрос зарегистрированного биндинга
(например, `tryResolve` для асинхронного) по-прежнему бросает исключение.
См. [API разрешения зависимостей](/ru/dependency-resolution-api/).

## Почему внутри `builder` модуля возникает `Can't resolve dependency`?

Биндинги в `builder` регистрируются последовательно, поэтому тип, привязанный через
`toInstance`, не может вызвать `scope.resolve<T>()` для другого типа из того же `builder` —
тот ещё не доступен. Либо соберите цепочку вручную до вызова `toInstance`, либо используйте
`toProvide` / `toProvideAsync`, которые разрешают зависимости лениво.
См. [Привязка (Binding)](/ru/core-concepts/binding/).

## Имеет ли смысл `.singleton()` после `.toInstance()`?

Нет. Объект из `toInstance()` и так единственный экземпляр, который возвращается при каждом
resolve. `.singleton()` важен только для провайдеров вроде `toProvide` / `toProvideAsync`.

## Почему синглтон с параметрами игнорирует новые params?

С `.toProvideWithParams(...).singleton()` параметры использует только **первый**
`resolve<T>(params: ...)`; все последующие вызовы возвращают закэшированный экземпляр.
Уберите `.singleton()`, если нужен новый экземпляр на каждые params.

## Подскоуп закрыт, а мой `Disposable` не освободился. Почему?

`Disposable` принадлежит скоупу, который **объявляет его биндинг**, а не тому, через который
его получили. Получение зависимости родителя через подскоуп не передаёт владение. Объявляйте
биндинг в скоупе, время жизни которого совпадает с ресурсом.
См. [Disposable → Владение](/ru/core-concepts/disposable/#владение-какой-скоуп-что-освобождает).

## Как обнаружить циклические зависимости?

Откройте скоуп через `CherryPick.openSafeRootScope()` или вызовите
`scope.enableCycleDetection()` для одного скоупа; `CherryPick.enableGlobalCrossScopeCycleDetection()`
отслеживает циклы между скоупами. Цикл приводит к `CircularDependencyException` с полной
цепочкой. Включайте проверку в debug и тестах и отключайте в продакшене.
См. [Обнаружение циклов](/ru/advanced-features/circular-dependency-detection/).

## Замедляется ли разрешение зависимостей с ростом приложения?

Нет. Начиная с версии 3.0.0 CherryPick хранит Map-индекс биндингов, поэтому `resolve<T>()` и
связанные вызовы работают за O(1) независимо от количества модулей и биндингов в скоупе.
Раньше библиотека перебирала все модули и биндинги. Изменение внутреннее, API не изменился.

## Генератор ничего не создаёт для моего `@module`. Чего не хватает?

Проверьте три вещи: директиву `part '<file>.module.cherrypick.g.dart';`, что класс
`extends Module` и объявлен `abstract`, и что у каждого метода есть `@provide` или `@instance`.
Затем перезапустите `dart run build_runner build --delete-conflicting-outputs`.
[`cherrypick_lint`](/ru/linting/) сообщает обо всём этом ещё до запуска кодогенерации.
См. [Аннотации](/ru/using-annotations/).

## Как использовать CherryPick во Flutter?

Оберните приложение в `CherryPickProvider` из `cherrypick_flutter` и получайте скоупы через
`CherryPickProvider.of(context).openRootScope()` или `.openSubScope(scopeName: ...)`.
См. [Быстрый старт](/ru/getting-started/#использование-во-flutter).
