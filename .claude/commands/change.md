Задача: $ARGUMENTS

Ты — оркестратор: код сам не пишешь, передаёшь контекст субагентам и следишь за процессом. Правила — `CLAUDE.md`.

0. **Ветка.** `git branch --show-current`. Работа — в отдельной ветке от актуального `develop`. Если ты на `master`/`develop` или ветка отстаёт — скажи пользователю и предложи команду; без согласия ветки не создавай.

1. **di-architect** — передай задачу (номер issue — прочитай через `gh issue view`). Он подтверждает поведение прогонами и готовит `openspec/changes/<change-id>/` с задачами `[core]`, `[codegen]`, `[lint]`, `[integrations]`, `[bench]`, `[docs]`.
   **Стоп:** покажи пользователю кратко proposal, результаты прогонов, ломающее ли изменение и для кого, список задач и открытые вопросы. Дальше — только после одобрения.

2. **Реализация по `tasks.md`** в порядке зависимостей (ядро и аннотации → генератор → линт и интеграции → документация):
   - `[core]` → **core-engineer**; `[codegen]` → **codegen-engineer**; `[lint]` → **lint-engineer**;
   - `[integrations]` → **integrations-engineer**; `[bench]` → **benchmark-engineer** (и после любого изменения горячего пути резолва);
   - `[docs]` → **docs-engineer** — после кода, ему нужны итоговые имена API.
   Независимые задачи разных пакетов можно запускать параллельно. Передавай путь к change, номера задач и отчёты предыдущих исполнителей.

3. **check-runner** — версия разработки; плюс нижняя версия матрицы (3.38.5), если менялись `environment`, `analyzer`, плагин линта или затронуты языковые возможности. FAIL → исполнителю пакета, повтор.

4. **code-reviewer** и **api-reviewer** — параллельно; обоим путь к change, diff и отчёт check-runner.

5. CHANGES REQUESTED → раздай BLOCKER и MAJOR исполнителям по зонам, затем шаги 3–4. Максимум 3 итерации; если блокеры остаются — остановись и покажи их пользователю.

6. **Итог пользователю:** что сделано; change-id и статус `tasks.md`; изменённые пакеты и ожидаемый semver-бамп каждого; таблица проверок по версиям Flutter; замеры бенчмарка, если были; вердикты и оставшиеся MINOR/NIT; черновик сообщения коммита (Conventional Commits, `scope` пакета, описание по-русски).

Без явной просьбы: не делать `git commit`/`push`, не открывать PR, не архивировать change, не запускать `melos version` и публикацию.
