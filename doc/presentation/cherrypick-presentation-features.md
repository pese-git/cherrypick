# Три понятия, и это всё

```text
Binding   — правило: как создать объект типа T
            bind<ApiClient>().toProvide(() => ApiClient())

Module    — набор биндингов, который можно передать как объект
            class NetworkModule extends Module { ... }

Scope     — узел дерева: живёт, пока не закрыт, и держит свои объекты
            root ── session ── order
```

**Всё остальное в библиотеке — уточнения к этим трём.**

<!--
Заметки спикера · 1,5 мин

— Произнесите главную мысль: понятий ровно три, и это был осознанный
   выбор автора — вложенные скоупы стоят команде трёх новых слов,
   а не пятнадцати.
— [ЗАМЕНИТЬ: перерисуйте схему графикой — это опорный слайд, к нему

# Рабочий код через минуту после установки

```dart
class AppModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().toProvide(() => ApiClient()).singleton();
  }
}

void main() {
  final root = CherryPick.openRootScope()..installModules([AppModule()]);

  final api = root.resolve<ApiClient>();
}
```

**Три шага:** объявить модуль → поставить его в скоуп → попросить объект

<!--
Заметки спикера · 1,5 мин

— Это первый код в колоде, и он полный: копируется и работает.
— Обратите внимание на каскад `..installModules` — installModules
   возвращает сам Scope, поэтому цепочка читается как одно выражение.
— `.singleton()` здесь не случайно: без него на каждый resolve
   создавался бы новый ApiClient. Про это следующий слайд.
-->

---

# Виды биндингов

```dart
bind<Config>().toInstance(config);                    // готовый объект
bind<ApiClient>().toProvide(() => ApiClient());       // фабрика
bind<Db>().toProvide(() => Db()).singleton();         // один на скоуп
```

| | когда создаётся | сколько экземпляров | живёт в скоупе |
|---|---|---|---|
| `toInstance` | сразу при установке модуля | один | **да** |
| `toProvide` | при первом `resolve` | **новый на каждый resolve** | нет |
| `toProvide().singleton()` | при первом `resolve` | один | **да** |

> Это самая частая причина недоумения: «почему у меня два разных
> репозитория». Ответ — забытый `.singleton()`

<!--
Заметки спикера · 2 мин

— САМЫЙ ПРАКТИЧЕСКИ ВАЖНЫЙ СЛАЙД БЛОКА. Именно здесь люди ошибаются.
— Проговорите последний столбец: скоуп держит только `toInstance` и
   синглтоны. Фабричные объекты принадлежат тому, кто их попросил,
   и закрытие скоупа их не касается.
— Полезный ориентир из практики: в боевом банковском приложении на
   1000 биндингов около 60% — фабрики. То есть большинство объектов
   в скоупе не живёт, и это нормально.
— `toInstance` создаётся В МОМЕНТ УСТАНОВКИ модуля. Если объект
   дорогой — берите `toProvide().singleton()`, он ленивый.
-->

---

# Именованные биндинги

```dart
class ApiModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().withName('prod').toProvide(() => ApiClient('api.example.com'));
    bind<ApiClient>().withName('mock').toProvide(() => ApiClient('localhost'));
  }
}

final api = scope.resolve<ApiClient>(named: 'prod');
```

**Зачем:** две реализации одного интерфейса живут рядом, а выбор делается в точке использования — не в модуле

<!--
Заметки спикера · 1 мин

— Порядок вызовов в цепочке свободный: `withName` можно ставить и до,
   и после `toProvide`. Показывайте один стиль, чтобы не путать.
— Реальный пример: два `Dio` — для auth-зоны и для non-auth. Или
   боевой и демо-источник данных, переключаемые флагом.
-->

# Параметры времени выполнения

```dart
class OrderModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<OrderRepo>().toProvideWithParams(
      (params) => OrderRepo(id: params as String, api: currentScope.resolve<ApiClient>()),
    );
  }
}

final repo = scope.resolve<OrderRepo>(params: 'order-42');
```

**Зачем:** объект, которому нужен аргумент, известный только в рантайме — id заказа, номер счёта

> Это то, что в типизированных DI выражается тяжелее всего.
> Цена — `params` имеет тип `dynamic`

<!--
Заметки спикера · 1,5 мин

— Назовите цену честно: `params` — `dynamic`, компилятор здесь не
   помогает. Приводите к своему типу сразу в биндинге, как на слайде.
— Альтернатива, если параметров много: передавайте свой класс-запрос
   вместо строки, тогда `params as OrderQuery` читается лучше.
— ОСТОРОЖНО с `.singleton()` на параметрическом биндинге: первый
   резолв закеширует объект вместе с первым параметром, и следующий
   запрос с другим id вернёт не то, что вы ждёте. В библиотеке про это
   есть предупреждение в документации к `singleton()`.
-->

---

# Асинхронные зависимости

```dart
class StorageModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<Database>().toProvideAsync(() async => Database.open('app.db')).singleton();
  }
}

final db = await scope.resolveAsync<Database>();
```

**Зачем:** `Database.open()`, `SharedPreferences.getInstance()` — их нельзя создать синхронно

**`toProvideAsync` + `resolveAsync`** — пара; синхронный `resolve` на async-биндинге бросит исключение

<!--
Заметки спикера · 1,5 мин

— Пара обязательна: объявили асинхронно — резолвите асинхронно.
— `toProvide` принимает `FutureOr<T> Function()`, поэтому
   `toProvide(() async => ...)` технически работает, но использует
   рантайм-детект типа. `toProvideAsync` принимает строго `Future<T>`:
   типобезопасно и без оверхеда. Для async-биндингов всегда
   предпочитайте `toProvideAsync`.
— Полезная деталь 4.0: если async-синглтон упал при инициализации,
   следующий resolveAsync попробует создать его заново, а не вернёт
   ту же ошибку навсегда.
-->

---

# Когда зависимости может не быть

```dart
final analytics = scope.tryResolve<Analytics>();   // null, если не зарегистрирован
analytics?.track('screen_open');

final db = await scope.tryResolveAsync<Database>();
```

**`resolve`** — бросает `StateError`, если биндинга нет. Это правильно для обязательных зависимостей: падать надо громко

**`tryResolve`** — возвращает `null`. Для необязательных: аналитика, дебажные инструменты, фича за флагом

> Не превращайте `tryResolve` в способ прятать ошибки конфигурации.
> Если объект нужен всегда — пусть падает

<!--
Заметки спикера · 1 мин

— Правило, которое стоит закрепить в команде: `tryResolve` только там,
   где отсутствие зависимости — штатный сценарий. Во всех остальных
   местах `resolve`, потому что тихий null уезжает в прод.
— ТОЧНОСТЬ (уточнено в dev.4): `tryResolve` возвращает `null` строго
   только если биндинг не зарегистрирован. Если биндинг зарегистрирован,
   но resolver не настроен (незавершённый биндинг) — это `StateError`,
   а не null. Не прячьте ошибки конфигурации за `tryResolve`.
-->

# Зачем дерево, а не один контейнер

```text
root                      ← всё время работы приложения
 │  ApiClient, Analytics
 │
 ├── session              ← от логина до логаута
 │    │  Profile, Wallet
 │    │
 │    ├── order-7         ← пока выполняется заказ
 │    └── order-9         ← второй заказ, независимо
 │
 └── nonAuth              ← экран входа
```

**Закрыли `session` — ушло всё поддерево.** Один вызов вместо обхода списка сервисов

<!--
Заметки спикера · 2 мин

— Ключевая мысль: скоуп — это не «папка для сервисов», а ВРЕМЯ ЖИЗНИ.
   Ветка дерева = группа объектов с общей судьбой.
— Обратите внимание на `order-7` и `order-9`: они сиблинги, живут
   одновременно и не знают друг о друге. Это то, чего не даёт стек.
— [ЗАМЕНИТЬ: перерисуйте графикой]
-->

# Как открыть и закрыть скоуп

```dart
final root = CherryPick.openRootScope();

final session = root.openSubScope('session')..installModules([SessionModule()]);
final order   = session.openSubScope('order-7')..installModules([OrderModule()]);

await root.closeSubScope('session');     // закрыли сессию и все заказы под ней
```

**Тот же скоуп по пути, из любого места кода:**

```dart
final order = CherryPick.openScope(scopeName: 'session.order-7');
await CherryPick.closeScope(scopeName: 'session');
```

<!--
Заметки спикера · 2 мин

— Два стиля дают один результат. По ссылке — когда скоуп рядом; по
   пути — когда вы в другом слое и родителя под рукой нет.
— `openScope` и `openSubScope` ИДЕМПОТЕНТНЫ: повторный вызов с тем же
   именем возвращает существующий скоуп, а не создаёт второй. На это
   удобно опираться — не надо хранить ссылки.
— Разделитель по умолчанию точка, меняется параметром `separator`.
— И `CherryPick.openScope`, и `CherryPick.closeScope` помечены
   `@experimental`: при строгих линтах вы получите предупреждение
   `experimental_member_use` на каждом вызове. Проверено — это
   единственное замечание анализатора на весь код этой колоды.
   Если оно мешает, работайте по ссылке (`openSubScope`/
   `closeSubScope`), там пометки нет.
-->

---

# Ребёнок видит родителя

```dart
class SessionModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<Wallet>().toProvide(
      () => Wallet(currentScope.resolve<ApiClient>()),   // ApiClient живёт в root
    ).singleton();
  }
}
```

**Резолв идёт вверх по дереву:** не нашли в своём скоупе — спрашиваем родителя, потом его родителя, до корня

**Обратно — нет.** Из `root` не видно того, что объявлено в `session`. Это не ограничение, а то, что делает время жизни предсказуемым

<!--
Заметки спикера · 1,5 мин

— Проговорите правило одной фразой: зависимости текут вниз, время
   жизни — снизу вверх. Долгоживущий объект не может зависеть от
   короткоживущего, и дерево вам этого не даст.
— Отсюда практический вывод: если сервису из root нужны данные
   сессии — передавайте их аргументом метода, а не через DI.
-->

# Освобождение ресурсов: Disposable

```dart
class OrderTracker implements Disposable {
  final StreamSubscription _sub;
  OrderTracker(this._sub);

  @override
  Future<void> dispose() async => _sub.cancel();
}
```

**Реализовали интерфейс — закрытие скоупа дождётся вашей уборки.** `closeSubScope` рекурсивно закрывает поддерево и `await`-ит каждый `dispose()`

> Память освободит и GC. `Disposable` нужен для другого: закрыть сокет,
> отменить подписку, сбросить буфер — **в момент** закрытия скоупа,
> а не когда-нибудь

<!--
Заметки спикера · 2 мин

— ВАЖНАЯ ТОЧНОСТЬ, иначе вы пообещаете не то. Отсутствие Disposable
   не создаёт утечки памяти: скоуп чистит индекс биндингов и кэш
   синглтонов, дальше объекты собирает GC обычным порядком. Это
   проверено пробой на реальном приложении.
— Что действительно даёт Disposable — ДЕТЕРМИНИРОВАННОЕ закрытие
   ресурса. Сокет соберётся сборщиком, но `disconnect()` до этого
   никто не позовёт.
— УТОЧНЕНИЕ dev.4 (задокументировано): скоуп dispose-ит только те
   объекты, которые создали ЕГО СОБСТВЕННЫЕ биндинги. Если зависимость
   разрешена через родительский скоуп — она зарегистрирована там и
   dispose-ится там. Дочерний скоуп её не трогает.
— ИМЯ МЕТОДА: у CherryPick это `dispose()`. У `get_it` в похожем
   интерфейсе — `onDispose()`. Если переходите с get_it, это первое,
   на чём спотыкаются.
— И честное предупреждение команде: пропуск `Disposable` не ловится
   ничем — ни компилятором, ни линтером. Это дисциплина, а не гарантия.
-->

# Модуль — это объект

```dart
final modules = <Module>[
  NetworkModule(baseUrl: config.apiUrl),
  if (config.useMocks) MockApiModule() else RealApiModule(),
  ...featurePackages.map((p) => p.module),
];

scope.installModules(modules);
```

**Что из этого следует:** модуль можно собрать в список, передать параметром, выбрать по условию, поставить в два разных скоупа и протестировать отдельно

**`dropModules()`** — снять все модули со скоупа, не закрывая сам скоуп

<!--
Заметки спикера · 1,5 мин

— Это то, чего не даёт функция регистрации: список объектов можно
   строить в рантайме, а функцию — нет.
— `dropModules` + `installModules` — рабочий приём для переключения
   реализации на живом приложении: например смена источника данных
   с боевого на демо без перезапуска.
-->

# Граф из пакетов

```dart
// в пакете feature_payments
class PaymentsModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<PaymentsRepo>().toProvide(() => PaymentsRepo(currentScope.resolve<ApiClient>())).singleton();
  }
}

// в приложении
session.installModules([PaymentsModule(), OrdersModule(), ChatModule()]);
```

**Пакет ничего не знает о приложении** — он отдаёт `Module` и требует только то, что резолвит из скоупа

> Так собирается монорепозиторий: в боевом проекте на 67 пакетов
> 97% биндингов приносят фичевые пакеты, приложение — 3%

<!--
Заметки спикера · 1,5 мин

— Слайд для тех, у кого большой проект. Главное — направление
   зависимости: пакет не импортирует приложение.
— Цифра 97/3 из реального банковского монорепо, её можно называть.
— Практика: держите в пакете один публичный Module и не экспортируйте
   внутренние классы — тогда состав фичи виден одним объектом.
-->

# Подмена в тестах

```dart
class TestOverridesModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().toInstance(MockApiClient());
  }
}

setUp(() {
  scope = CherryPick.openRootScope()
    ..installModules([AppModule(), TestOverridesModule()]);
});

tearDown(() => CherryPick.closeRootScope());
```

**Подмена — это ещё один модуль поверх боевых.** Тот же механизм, что в проде, а не отдельный API для тестов

<!--
Заметки спикера · 2 мин

— ПОРЯДОК ВАЖЕН: последний установленный биндинг того же типа
   перекрывает предыдущие. Модуль с подменами ставится ПОСЛЕ боевых.
— `tearDown` с закрытием рут-скоупа обязателен, иначе тесты потекут
   друг в друга: скоуп-то глобальный.
— Скажите вслух, зачем это так сделано: не нужно учить второй API
   ради тестов, и тестовая сборка графа устроена как боевая.

# Кодогенерация: зачем

**Проблема:** модуль на 50 биндингов — это 50 раз `bind<T>().toProvide(() => T(scope.resolve<A>(), scope.resolve<B>()))`. Машинная работа

```dart
@module()
abstract class AppModule extends Module {
  @provide()
  @singleton()
  PaymentsRepo repo(ApiClient api, Logger log) => PaymentsRepo(api, log);
}
```

**Аргументы метода становятся `currentScope.resolve<...>()` в сгенерированном коде.** Пишете конструктор — получаете биндинг

<!--
Заметки спикера · 1,5 мин

— Главное, что надо понять: генератор не меняет модель. На выходе
   тот же `bind<T>().toProvide(...)`, просто написанный машиной.
— Поэтому кодогенерацию можно включить на одном модуле, а остальные
   оставить рукописными. Смешивать безопасно.

# Кодогенерация: как подключить

# Все аннотации

| Аннотация | Что делает |
|---|---|
| `@module()` | класс — DI-модуль, для него генерируется `$Имя` |
| `@provide()` | метод регистрируется как фабрика |
| `@instance()` | метод отдаёт готовый объект (`toInstance`) |
| `@singleton()` | один экземпляр на скоуп |
| `@named('...')` | именованный биндинг |
| `@params()` | параметр приходит при резолвинге |
| `@injectable()` | класс участвует в инъекции полей |
| `@inject()` | поле заполняется автоматически |
| `@scope('...')` | поле резолвится из указанного скоупа |

**Генератор проверяет за вас:** `@instance` и `@provide` вместе — ошибка; `@params` без `@provide` — ошибка

# Инъекция полей


# Циклические зависимости

```dart
// A зависит от B, B зависит от A — внятное исключение с цепочкой A → B → A

// Вариант 1: включить оба детектора для конкретного скоупа сразу
final scope = CherryPick.openGlobalSafeScope(scopeName: 'session');

// Вариант 2: включить раздельно
scope.enableCycleDetection();        // локальный (внутри скоупа)
scope.enableGlobalCycleDetection();  // кросс-скоуп (через границы)
```

**Два уровня:**

**Локальный** — цикл внутри одного скоупа.
`scope.enableCycleDetection()` или `CherryPick.enableGlobalCycleDetection()` (для всех)

**Кросс-скоуп** — цикл через границы скоупов.
`scope.enableGlobalCycleDetection()` или `CherryPick.enableGlobalCrossScopeCycleDetection()` (для всех)

**`openGlobalSafeScope`** — включает оба детектора в одном вызове

**Что получите вместо стек-оверфлоу:** исключение с цепочкой `A → B → A`

<!--
Заметки спикера · 1,5 мин

— По умолчанию детект ВЫКЛЮЧЕН, и это осознанно: он стоит времени
   на каждом резолве. Включайте в debug-сборке и в тестах, в проде
   выключайте.
— ВАЖНО — неочевидная номенклатура API: `CherryPick.enableGlobalCycleDetection()`
   включает ЛОКАЛЬНЫЙ детект сразу на всех текущих и новых скоупах.
   А `CherryPick.enableGlobalCrossScopeCycleDetection()` — кросс-скоуп.
   На уровне одного Scope: `enableCycleDetection()` = локальный,
   `enableGlobalCycleDetection()` = кросс-скоуп.
— Честно скажите про сравнение: у yx_scope это статический линтер,

   В dev.4 цепочка корректно сохраняется через async-границы.

# Кто закрывает скоуп экрана

```dart
class OrderScreenState extends State<OrderScreen> {
  late final Scope _scope;

  @override
  void initState() {
    super.initState();
    _scope = CherryPick.openScope(scopeName: 'session.order-${widget.id}')
      ..installModules([OrderModule(widget.id)]);
  }

  @override
  void dispose() {
    CherryPick.closeScope(scopeName: 'session.order-${widget.id}');
    super.dispose();
  }
}
```

**Или скоупом управляет роутер** — guard на входе в поток открывает, на выходе закрывает

<!--
Заметки спикера · 2 мин

— Два рабочих подхода, и выбор не косметический:
   • экран владеет скоупом — просто, но время жизни привязано к UI;
   • роутер владеет скоупом — сложнее, зато скоуп переживает
     пересоздание экрана и покрывает многоэкранный процесс.
— В большом банковском приложении выбран второй: guard'ы роутера
   открывают скоупы процессов оплаты, подписания, генформ.
— НЕ ЗАБУДЬТЕ про `dispose` в State: если скоуп открыт в initState
   и не закрыт, он останется висеть после ухода с экрана.
-->

# Три рецепта, которые нужны всем

**Логаут — одной строкой**

```dart
await CherryPick.closeScope(scopeName: 'session');
```

**Две сессии одновременно** — два сабскоупа на одном уровне

```dart
root.openSubScope('session-a')..installModules([SessionModule(userA)]);
root.openSubScope('session-b')..installModules([SessionModule(userB)]);
```

**Экран-процесс** — скоуп на весь поток, а не на экран: открыли на входе в оплату, закрыли на выходе, промежуточные экраны его переиспользуют

<!--
Заметки спикера · 2 мин

— Эти три случая покрывают почти все вопросы, которые приходят
   от команды в первый месяц.
— Про две сессии: подчеркните, что это не хак, а прямое следствие
   дерева — ветки независимы по определению.
-->

# Чего не делать

**Не кладите всё в корневой скоуп.** Тогда дерево вырождается в глобальный контейнер, и время жизни снова становится «пока живёт процесс»

**Не резолвите в конструкторе модуля** — только внутри `builder`, иначе объект создастся при установке, а не при запросе

**Не держите ссылку на закрытый скоуп.** После `closeSubScope` объект скоупа непригоден, берите заново по имени

**Не ставьте `.singleton()` на параметрический биндинг** — закешируется первый параметр

**Не наследуйте `SilentCherryPickObserver`** — наблюдатель замолчит, нужен `implements`

<!--
Заметки спикера · 2 мин

— Все пять — не теория, а грабли из практики.
— Первый пункт самый частый и самый дорогой: команда добавляет модули
   в корень, потому что «так проще», и через год логаут снова
   протекает. Задавайте на код-ревью один вопрос: почему это в корне?

# Резерв 1: миграция 3.x → 4.0

**Четыре breaking-изменения, все механические:**

**1.** Удалены `Instance<T>` и `ProviderWithParams<T>` → используйте `ProviderFactory<T>` и `ProviderFactoryWithParams<T>`

**2.** `ProviderFactory<T>` теперь строго синхронный — асинхронное только через `toProvideAsync`

**3.** `toProvideAsync` принимает `Future<T>`, а не `FutureOr<T>`

**4.** `InstanceResolver` и `ProviderResolver` больше не экспортируются — это внутренности

**5.** `toInstanceAsync` объявлен устаревшим → `toInstance`

**Изменение поведения:** async-синглтон после ошибки инициализации пробуется заново, а не кеширует ошибку

# Резерв 2: полный API скоупа

| | |
|---|---|
| `resolve<T>({named, params})` | бросает, если биндинга нет |
| `tryResolve<T>({named, params})` | `null` только если биндинга нет |
| `resolveAsync<T>` / `tryResolveAsync<T>` | асинхронные пары |
| `openSubScope(name)` | открыть или получить дочерний |
| `closeSubScope(name)` | закрыть вместе с поддеревом |
| `installModules([...])` / `dropModules()` | поставить и снять модули |
| `dispose()` | закрыть сам скоуп |
| `enableCycleDetection()` | локальный детект (внутри скоупа) |
| `enableGlobalCycleDetection()` | кросс-скоуп детект (через границы) |

**Статические хелперы CherryPick:**

| | |
|---|---|
| `openRootScope()` / `closeRootScope()` | корневой скоуп |
| `openScope(scopeName:)` / `closeScope(scopeName:)` | по пути `@experimental` |
| `openSafeScope(scopeName:)` | с локальным детектом |
| `openGlobalSafeScope(scopeName:)` | с локальным + кросс-скоуп детектом |
| `setGlobalObserver(observer)` | глобальный наблюдатель |
| `enableGlobalCycleDetection()` | локальный детект для всех скоупов |
| `enableGlobalCrossScopeCycleDetection()` | кросс-скоуп детект для всех |
| `getCurrentResolutionChain({scopeName})` | текущая цепочка резолвинга |
| `getGlobalResolutionChain()` | цепочка кросс-скоуп детектора |

# Резерв 3: почему не кодогенерация по умолчанию

**Кодогенерация в CherryPick опциональна, и это выбор, а не недоделка**

**Что вы получаете без неё:** ноль настройки, ноль `build_runner` в CI, работающий код через минуту после `pub add`

**Что теряете:** пишете биндинги руками; часть ошибок всплывает в рантайме, а не при генерации

**Как решить у себя:** включайте генерацию на модулях, где больше 20 биндингов, остальное оставьте руками. Смешивать безопасно — на выходе один и тот же `bind<T>()`

---

# Резерв 4: производительность

**Что известно точно:** регистрация 1000 биндингов из 43 модулей — около 5,6 мс на устройстве в AOT, меньше 1% времени до первого кадра

**Что из этого следует:** DI на типичном приложении не узкое место, и оптимизировать сборку графа обычно незачем

**Где всё же можно сэкономить:** `toInstance` создаёт объект при установке модуля. Если таких много и они дорогие — переведите в `toProvide().singleton()`, он ленивый

**Бенчмарк** лежит в репозитории (`benchmark_di`), запускается одной командой

# Резерв 5: частые вопросы

**«Нужно ли `await` у `closeScope`, если Disposable нигде не реализован?»**
Формально нет, но пишите `await` всегда: добавите `Disposable` через месяц и не вспомните про это место

**«Скоуп глобальный — это же синглтон-контейнер?»**
Да, дерево живёт в статике. Поэтому в тестах обязателен `closeRootScope()` в `tearDown`

**«Можно ли мигрировать постепенно с get_it?»**
Да: новые фичи на скоупах, легаси остаётся, мост в один биндинг —
`bind<LegacyService>().toProvide(() => GetIt.I<LegacyService>())`

**«Работает в чистом Dart, без Flutter?»**
Да, `cherrypick` не зависит от Flutter. `cherrypick_flutter` — отдельный пакет
