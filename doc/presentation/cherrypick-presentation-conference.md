# Два вопроса, которые определяют дизайн DI

## Чем задано время жизни?

```text
Ничем (процесс)  →  Деревом виджетов  →  Подписками  →  Стеком  →  Деревом скоупов
   kiwi              provider             riverpod      get_it      yx_scope
  (глобальные)                                                     cherrypick
```

## Когда узнаёте о ненайденной зависимости?

```text
Компиляция  →  Генерация  →  Рантайм  →  У пользователя
  yx_scope    injectable    get_it
              cherrypick_  cherrypick
              gen, kiwi_gen
```

**Это компромисс, не рейтинг.** Левее — больше гарантий, правее — больше гибкости

# Выбор: дерево скоупов

**Задача:** управлять памятью в мобильном банке

Экран входа — одни зависимости.
Сессия пользователя — другие, грузятся при логине.
Платёж — третьи, грузятся при открытии экрана.
Экран закрыт → зависимости освободились.

```text
root  ─── ApiClient (живёт всегда)
  └─ session ─── профиль, лимиты   ← логин  → closeScope при логауте
        └─ payment ─── PaymentRepo  ← экран  → closeScope при закрытии
```

```dart
await CherryPick.closeScope('payment');
// CherryPick сам вызовет dispose() на всех Disposable в скоупе
```

# Три понятия, и это всё

```text
Binding   — правило: как создать объект типа T
            bind<ApiClient>().toProvide(() => ApiClient())

Module    — набор биндингов, который можно передать как объект
            class NetworkModule extends Module { ... }

Scope     — узел дерева: живёт, пока не закрыт, держит свои объекты
            root ── session ── order
```

**Всё остальное — уточнения к этим трём.**

<!--

   Scope = узел с временем жизни. Три разных сущестности, три разных задачи.

# Рабочий код через минуту после установки

```dart
class AppModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().toProvide(() => ApiClient()).singleton();
  }
}

void main() {
  final root = CherryPick.openRootScope()..installModules([AppModule()]);
  final api  = root.resolve<ApiClient>();
}
```

**Три шага:** объявить модуль → поставить в скоуп → попросить объект

<!--
Заметки спикера · 1,5 мин

— Код в этой части компилируется.
— Каскад `..installModules` — installModules возвращает сам Scope,
   цепочка читается как одно выражение.
— `.singleton()` здесь не случайно: без него каждый `resolve` даст
   новый ApiClient. Следующий слайд — про это.
-->

---

# Виды биндингов

```dart
bind<Config>().toInstance(config);                    // готовый объект
bind<ApiClient>().toProvide(() => ApiClient());       // фабрика
bind<Db>().toProvide(() => Db()).singleton();         // один на скоуп
```

| | когда создаётся | сколько экземпляров | живёт в скоупе |
|---|---|---|---|
| `toInstance` | при установке модуля | один | **да** |
| `toProvide` | при первом `resolve` | **новый на каждый** | нет |
| `toProvide().singleton()` | при первом `resolve` | один | **да** |

> Самая частая причина двух разных репозиториев — забытый `.singleton()`

<!--
Заметки спикера · 2 мин

— Самый практически важный слайд раздела.
— Ключевой столбец — «живёт в скоупе». Именно он определяет, что
   уберётся при закрытии, а что нет. Скоуп чистит только те объекты,
   которые создали его собственные биндинги.
— В боевом проекте: ~60% биндингов — фабрики. Большинство объектов
   в скоупе не живут — и это нормально.
-->

# Зачем дерево, а не один контейнер

```text
root                      ← всё время работы приложения
 │  ApiClient, Analytics
 │
 ├── session              ← от логина до логаута
 │    │  Profile, Wallet
 │    │
 │    ├── order-7         ← пока выполняется заказ
 │    └── order-9         ← второй заказ, независимо
 │
 └── nonAuth              ← экран входа
```

**Закрыли `session` — ушло всё поддерево.** Один вызов вместо обхода списка

<!--
Заметки спикера · 2 мин

— Ключевая мысль: скоуп — это не «папка для сервисов», а ВРЕМЯ ЖИЗНИ.
   Ветка = группа объектов с общей судьбой.
— `order-7` и `order-9` — сиблинги. Они живут одновременно и не знают
   друг о друге. Именно это и нужно для двух параллельных заказов —
   два заказа в одной сессии, не мешающих друг другу.
— [ЗАМЕНИТЬ: перерисуйте графикой — её фотографируют]
-->

# Как открыть и закрыть скоуп

```dart
final root    = CherryPick.openRootScope();
final session = root.openSubScope('session')..installModules([SessionModule()]);
final order   = session.openSubScope('order-7')..installModules([OrderModule()]);

await root.closeSubScope('session');   // закрыли сессию и все заказы под ней
```

**Тот же скоуп по имени из любого слоя кода:**

```dart
final scope = CherryPick.openScope(scopeName: 'session.order-7');
await CherryPick.closeScope(scopeName: 'session');
```

<!--
Заметки спикера · 2 мин

— Два стиля, один результат. По ссылке — когда скоуп рядом; по
   пути — когда вы в другом слое и ссылку хранить неудобно.
— `openScope` и `openSubScope` идемпотентны: повторный вызов с тем же
   именем возвращает существующий скоуп. На это можно опираться.
— `openScope` / `closeScope` помечены `@experimental`: три предупреждения
   `experimental_member_use` — единственное замечание анализатора
   на весь код этой колоды.
-->

# Ребёнок видит родителя

```dart
class SessionModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<Wallet>().toProvide(
      () => Wallet(currentScope.resolve<ApiClient>()),   // ApiClient в root
    ).singleton();
  }
}
```

**Резолв идёт вверх по дереву:** не нашли в своём — спрашиваем родителя, до корня

**Обратно — нет:** из `root` не видно того, что объявлено в `session`

> Зависимости текут вниз, время жизни — снизу вверх.
> Долгоживущий объект не может зависеть от короткоживущего

<!--
Заметки спикера · 1,5 мин

— Правило работает как гравитация: оно встроено в дерево, его не
   надо помнить — нарушить его невозможно.
— Практический вывод: если сервису из root нужны данные сессии —
   передавайте их аргументом метода, а не через DI.
-->

# Освобождение ресурсов: Disposable

```dart
class OrderTracker implements Disposable {
  final StreamSubscription _sub;
  OrderTracker(this._sub);

  @override
  Future<void> dispose() async => _sub.cancel();
}
```

**Реализовали интерфейс — закрытие скоупа дождётся вашей уборки.**
`closeSubScope` рекурсивно обходит поддерево и `await`-ит каждый `dispose()`

> Память освободит GC. `Disposable` нужен для другого:
> закрыть сокет, отменить подписку — **в момент** закрытия, а не когда-нибудь

<!--
Заметки спикера · 2 мин

— Отсутствие Disposable не создаёт утечки памяти: скоуп чистит индекс
   биндингов и кэш синглтонов, GC делает остальное.
   Disposable — про детерминированное закрытие ресурса.
— Важная точность (dev.4): скоуп dispose-ит только объекты своих
   биндингов. Зависимость через родительский скоуп — дело родителя.
— Сравнение: get_it использует `onDispose()`, не `dispose()`.
   Это первое место, где спотыкаются при миграции.
-->

# Модуль — это объект

```dart
final modules = <Module>[
  NetworkModule(baseUrl: config.apiUrl),
  if (config.useMocks) MockApiModule() else RealApiModule(),
  ...featurePackages.map((p) => p.module),
];

session.installModules(modules);
```

**Модуль можно** передать параметром, выбрать по условию,
поставить в два разных скоупа, протестировать отдельно

**`dropModules()`** — снять модули со скоупа, не закрывая его

<!--
Заметки спикера · 1,5 мин

— Это то, чего не даёт функция регистрации: список объектов можно
   строить в рантайме, функцию — нет.
— `dropModules` + `installModules` = переключение реализации на живом
   приложении без перезапуска.
— Пример: в реальном монорепозитории на 67 пакетов приложение несёт
   ~3% биндингов, остальное приносят фичевые пакеты — каждый своим Module.
-->

```dart
class TestOverridesModule extends Module {
  @override

    bind<ApiClient>().toInstance(MockApiClient());
  }

setUp(() {
  scope = CherryPick.openRootScope()
    ..installModules([AppModule(), TestOverridesModule()]);
```

# Три рецепта, которые нужны всем

**Логаут — одной строкой**
```dart
await CherryPick.closeScope(scopeName: 'session');
```

**Две сессии одновременно** — два сабскоупа на одном уровне
```dart
root.openSubScope('session-a')..installModules([SessionModule(userA)]);
root.openSubScope('session-b')..installModules([SessionModule(userB)]);
```

**Экран-процесс** — скоуп открывается на входе в поток (оплата, подписание),
закрывается на выходе; промежуточные экраны его переиспользуют

<!--
Заметки спикера · 2 мин

— Три случая из практики, которые покрывают большинство вопросов
   в первый месяц работы с библиотекой.
— Про две сессии: это не хак — ветки независимы по определению
   дерева. Два заказа = два сиблинга (слайд «Зачем дерево»).
— Про процессный скоуп: открыть в guard-е роутера, закрыть в нём же.
   В реальном банковском приложении: 29 таких скоупов под сессионным.
-->

# Чего не делать

**Не кладите всё в корневой скоуп** — дерево вырождается в глобальный контейнер,
время жизни объектов снова становится «пока живёт процесс»

**Не резолвите в конструкторе модуля** — только внутри `builder`,
иначе объект создаётся при установке, а не при первом запросе

**Не держите ссылку на закрытый скоуп** — после `closeSubScope`
объект непригоден; берите по имени (`openScope` идемпотентен)

**Не ставьте `.singleton()` на параметрический биндинг** — закешируется первый параметр

**Не наследуйте `SilentCherryPickObserver`** — наблюдатель замолчит; нужен `implements`

<!--
Заметки спикера · 2 мин

— Пять пунктов — пять реальных граблей из практики, не теория.
— Первый — самый частый: «так проще» в моменте, а через год логаут
   снова протекает. Одно правило для код-ревью: «почему это в корне?»
-->

# Именованные биндинги

```dart
class ApiModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().withName('prod').toProvide(() => ApiClient('api.example.com'));
    bind<ApiClient>().withName('mock').toProvide(() => ApiClient('localhost'));
  }
}

final api = scope.resolve<ApiClient>(named: 'prod');
```

# Когда зависимости может не быть

```dart
final analytics = scope.tryResolve<Analytics>();   // null, если биндинга нет
analytics?.track('screen_open');
```

**`resolve`** — бросает `StateError`, если биндинга нет. Для обязательных зависимостей: падать надо громко

**`tryResolve`** — возвращает `null`. Для необязательных: аналитика, дебаг-инструменты, фичи за флагом

> Точность dev.4: `tryResolve` возвращает `null` строго только если биндинг
> не зарегистрирован. Незавершённый биндинг — это всё равно `StateError`

<!--
Заметки спикера · 1 мин

— Правило, которое стоит закрепить в команде: `tryResolve` только там,
   где отсутствие зависимости — штатный сценарий. Иначе `resolve`:
   тихий null уезжает в прод незамеченным.
-->

# Аннотации кодогенератора

| Аннотация | Что делает |
|---|---|
| `@module()` | класс — DI-модуль, генерируется `$Имя` |
| `@provide()` | метод регистрируется как фабрика |
| `@instance()` | метод отдаёт готовый объект (`toInstance`) |
| `@singleton()` | один экземпляр на скоуп |
| `@named('...')` | именованный биндинг |
| `@params()` | параметр приходит при резолвинге |
| `@injectable()` | класс участвует в инъекции полей |
| `@inject()` | поле заполняется автоматически |
| `@scope('...')` | поле резолвится из указанного скоупа |

**Генератор валидирует:** `@instance` и `@provide` вместе — ошибка; `@params` без `@provide` — ошибка

# Цена выбора

**Рантайм-проверка.** Забытый биндинг — ошибка при запуске, не при компиляции.
Дисциплина в регистрации и тесты покрывают это на практике

**Уборка ресурсов — дисциплина, не гарантия.** Компилятор не скажет,
что класс держит ресурс и не реализует `Disposable`

**Один мейнтейнер.** Автобусный фактор равен одному.
Apache 2.0: форкается без разрешения

> Эти три пункта — не недоработки. Это сознательные обмены:
> я выбрал более низкий входной барьер за счёт сдвига проверок вправо

<!--
Заметки спикера · 1,5 мин

— Говорите ровным тоном, без самоуничижения и без оправданий.
   Это не извинения — это описание сделки.
— Первый пункт: тесты + детект циклов в dev-сборке снимают большинство

# Резерв 1: «Чем отличаешься от yx_scope?»

**Общее:** дерево скоупов, чистый Dart, явное время жизни, вложенность, async

| | `yx_scope` | `cherrypick` |
|---|---|---|
| Доступ к зависимости | Типизированное поле `dep` | Резолвинг по типу |
| Когда ловится ошибка | Компиляция | Рантайм |
| Детект циклов | Статический линтер | Рантайм, по флагу |
| Именованные реализации | Через отдельные поля | `withName()` |
| Runtime-параметры | Через конструктор контейнера | `toProvideWithParams` |
| Кодогенерация | Нет принципиально | Опционально |

**Разные обмены, одна задача.** Нужны гарантии компилятора — берите `yx_scope`

# Резерв 2: полный API скоупа

|---|---|
| `resolve<T>({named, params})` | бросает, если биндинга нет |

# Резерв 3: миграция 3.x → 4.0

**Четыре breaking-изменения, все механические:**

**1.** Удалены `Instance<T>` и `ProviderWithParams<T>` → `ProviderFactory<T>`, `ProviderFactoryWithParams<T>`

**2.** `ProviderFactory<T>` теперь строго синхронный — асинхронное только через `toProvideAsync`

**3.** `toProvideAsync` принимает `Future<T>`, а не `FutureOr<T>`

**4.** `InstanceResolver` и `ProviderResolver` больше не экспортируются

**Изменение поведения:** async-синглтон после ошибки инициализации пробуется заново

# Резерв 5: «А производительность?»

**Что измерено:** 5,6 мс на сборку 1000 биндингов из 43 модулей в AOT —
меньше 1% от 608 мс до первого кадра

**Бенчмарк** в репозитории (`benchmark_di`), запускается одной командой

**Где get_it быстрее:** eager-синглтон (2,8 против 4,8 µs), override в дочернем скоупе

**Где cherrypick быстрее:** `AsyncChain` (247,8 против 15 033 µs у get_it)

**Практический вывод:** DI редко узкое место. Если стало — принесите кейс в issue
