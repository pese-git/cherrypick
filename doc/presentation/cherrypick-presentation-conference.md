# Ось первая: чем задано время жизни?

| | Кто решает | Где в ландшафте |
|---|---|---|
| **Ничто** | Никто: объект живёт всегда | `kiwi`, глобальные переменные |
| **Дерево виджетов** | Flutter: виджет ушёл — объект умер | `provider` |
| **Наличие слушателей** | Фреймворк: никто не смотрит — умер | `riverpod` |
| **Позиция в стеке** | Программист, явно, линейно: одна ветка | `get_it` |
| **Объявленная ветка** | Программист, явно, **несколько параллельно** | `yx_scope`, `cherrypick` |

**Ни одна клетка не лучше другой.**
Вопрос в том, какая форма времени жизни есть в вашем приложении

# Ось вторая: когда узнаете, что зависимости нет?

| | Инструмент | За что платите |
|---|---|---|
| **Компиляция** | `yx_scope` | Больше кода, меньше динамики |
| **Генерация** | `injectable`, `cherrypick_gen`, `kiwi_gen` | `build_runner` в сборке |
| **Рантайм** | `get_it`, `kiwi`, `cherrypick` | Ошибка при запуске |
| **У пользователя** | Любой инструмент без тестов | — |

**Обмен, а не победа:** слева — гарантии за счёт объёма кода, справа — динамика за счёт гарантий

**Это независимая ось.** Инструменты из одной клетки первой карты
могут стоять в разных клетках второй

# Где на карте CherryPick

## Дерево скоупов + рантайм-резолвинг + опциональная кодогенерация

```dart
  @override

final order = accountScope.openSubScope('order')    // 3. Scope
```

# Чем я за это заплатил

**Проверка в рантайме.** Забыли биндинг — узнаете при запуске, а не при компиляции. `yx_scope` этот класс ошибок закрывает, я — нет

**Детект циклов рантаймовый и по умолчанию выключен.** У `yx_scope` — статический линтер

**Уборка ресурсов не гарантирована ничем.** В моём же проекте `Disposable` не реализует ни один класс. Память при этом не течёт — её собирает GC, — но сокет закрывает не DI, а guard в роутере

**Один мейнтейнер против команды Яндекса.** Автобусный фактор равен одному, и это честный риск

**Почти нулевая известность.** Четыре статьи, около четырёх тысяч просмотров суммарно, ноль комментариев. Отсюда этот формат доклада

# Матрица выбора

**Приложение без смены контекста, нет логаута** → `get_it` или `kiwi`. Не усложняйте

**Состояние тесно связано с UI, нужен кеш и реактивность** → `riverpod`. Это его задача

**Объект принадлежит экрану и не переживает его** → `provider`

**Нужны скоупы и важнее всего гарантии компилятора** → `yx_scope`

**Нужны скоупы, важнее минимум понятий и динамика, готовы платить рантаймом** → `cherrypick`

# Задача 1: логаут

| Подход | Как |
|---|---|
| Глобальные переменные | Обойти все сервисы вручную |
| `kiwi` | `container.clear()` — стирает всё сразу, уборку зовёте сами |
| `provider` | Убрать поддерево из виджетов |

**Вот здесь подходы расходятся по-настоящему**

# Задача 4: асинхронная зависимость

**`Database.open()`, `SharedPreferences.getInstance()` — их нельзя создать синхронно**

| Подход | Как |
|---|---|
| Глобальные переменные | `await` в `main()` до `runApp` |
| `kiwi` | `await` до регистрации, потом `registerInstance` |
| `riverpod` | Естественно: `FutureProvider`, `AsyncValue` |
| `get_it` | `registerSingletonAsync` + `allReady()` |
| `yx_scope` | `rawAsyncDep` + явная `initializeQueue` с порядком |
| `cherrypick` | `toProvideAsync()` + `resolveAsync<T>()` |

**У `riverpod` асинхронность встроена в модель.** У остальных это отдельный механизм

# Три понятия, и это всё

```text
Binding   — правило: как создать объект типа T
            bind<ApiClient>().toProvide(() => ApiClient())

Module    — набор биндингов, который можно передать как объект
            class NetworkModule extends Module { ... }

Scope     — узел дерева: живёт, пока не закрыт, и держит свои объекты
            root ── session ── order
```

**Всё остальное в библиотеке — уточнения к этим трём.**

<!--

# Рабочий код через минуту после установки

```dart
class AppModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().toProvide(() => ApiClient()).singleton();
  }
}

void main() {
  final root = CherryPick.openRootScope()..installModules([AppModule()]);

  final api = root.resolve<ApiClient>();
}
```

**Три шага:** объявить модуль → поставить его в скоуп → попросить объект

<!--
Заметки спикера · 1,5 мин

— Это первый код в этой части, и он полный: копируется и работает.
— Каскад `..installModules` — installModules возвращает сам Scope,
   поэтому цепочка читается как одно выражение.
— `.singleton()` здесь не случайно: без него на каждый resolve
   создавался бы новый ApiClient.
-->

---

# Виды биндингов

```dart
bind<Config>().toInstance(config);                    // готовый объект
bind<ApiClient>().toProvide(() => ApiClient());       // фабрика
bind<Db>().toProvide(() => Db()).singleton();         // один на скоуп
```

| | когда создаётся | сколько экземпляров | живёт в скоупе |
|---|---|---|---|
| `toInstance` | сразу при установке модуля | один | **да** |
| `toProvide` | при первом `resolve` | **новый на каждый resolve** | нет |
| `toProvide().singleton()` | при первом `resolve` | один | **да** |

> Самая частая причина недоумения: «почему у меня два разных репозитория».
> Ответ — забытый `.singleton()`

<!--
Заметки спикера · 2 мин

— САМЫЙ ПРАКТИЧЕСКИ ВАЖНЫЙ СЛАЙД БЛОКА. Именно здесь ошибаются.
— В боевом банковском приложении на 1000 биндингов около 60% —
   фабрики. Большинство объектов в скоупе не живёт — это нормально.
— `toInstance` создаётся В МОМЕНТ УСТАНОВКИ модуля. Если объект
   дорогой — берите `toProvide().singleton()`, он ленивый.
-->

# Зачем дерево, а не один контейнер

```text
root                      ← всё время работы приложения
 │  ApiClient, Analytics
 │
 ├── session              ← от логина до логаута
 │    │  Profile, Wallet
 │    │
 │    ├── order-7         ← пока выполняется заказ
 │    └── order-9         ← второй заказ, независимо
 │
 └── nonAuth              ← экран входа
```

**Закрыли `session` — ушло всё поддерево.** Один вызов вместо обхода списка сервисов

<!--
Заметки спикера · 2 мин

— Ключевая мысль: скоуп — это не «папка для сервисов», а ВРЕМЯ ЖИЗНИ.
   Ветка дерева = группа объектов с общей судьбой.
— Обратите внимание на `order-7` и `order-9`: они сиблинги, живут
   одновременно. Это то, чего не даёт стек get_it — там одна ветка.

# Как открыть и закрыть скоуп

```dart
final root = CherryPick.openRootScope();

final session = root.openSubScope('session')..installModules([SessionModule()]);
final order   = session.openSubScope('order-7')..installModules([OrderModule()]);

await root.closeSubScope('session');   // закрыли сессию и все заказы под ней
```

**Тот же скоуп по пути, из любого места кода:**

```dart
final order = CherryPick.openScope(scopeName: 'session.order-7');
await CherryPick.closeScope(scopeName: 'session');
```

<!--
Заметки спикера · 2 мин

— Два стиля дают один результат. По ссылке — когда скоуп рядом; по
   пути — когда вы в другом слое и родителя под рукой нет.
— `openScope` и `openSubScope` ИДЕМПОТЕНТНЫ: повторный вызов с тем же
   именем возвращает существующий скоуп. На это можно опираться —
   не нужно хранить ссылки.
— `CherryPick.openScope` и `closeScope` помечены `@experimental`:
   получите предупреждение `experimental_member_use`. Три таких
   предупреждения — единственное замечание анализатора на весь
   код этой колоды.
-->

# Ребёнок видит родителя

```dart
class SessionModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<Wallet>().toProvide(
      () => Wallet(currentScope.resolve<ApiClient>()),   // ApiClient живёт в root
    ).singleton();
  }
}
```

**Резолв идёт вверх по дереву:** не нашли в своём скоупе — спрашиваем родителя, до корня

**Обратно — нет.** Из `root` не видно того, что объявлено в `session`. Это не ограничение, а то, что делает время жизни предсказуемым

<!--
Заметки спикера · 1,5 мин

— Правило одной фразой: зависимости текут вниз, время жизни —
   снизу вверх. Долгоживущий объект не может зависеть от
   короткоживущего, и дерево вам этого не даст.
— Практический вывод: если сервису из root нужны данные сессии —
   передавайте их аргументом метода, а не через DI.
-->

# Освобождение ресурсов: Disposable

```dart
class OrderTracker implements Disposable {
  final StreamSubscription _sub;
  OrderTracker(this._sub);

  @override
  Future<void> dispose() async => _sub.cancel();
}
```

**Реализовали интерфейс — закрытие скоупа дождётся вашей уборки.** `closeSubScope` рекурсивно закрывает поддерево и `await`-ит каждый `dispose()`

> Память освободит и GC. `Disposable` нужен для другого: закрыть сокет,
> отменить подписку — **в момент** закрытия скоупа, а не когда-нибудь

<!--
Заметки спикера · 2 мин

— ВАЖНАЯ ТОЧНОСТЬ. Отсутствие Disposable не создаёт утечки памяти:
   скоуп чистит индекс биндингов и кэш синглтонов, дальше GC.
   Что даёт Disposable — ДЕТЕРМИНИРОВАННОЕ закрытие ресурса.
— Уточнение dev.4: скоуп dispose-ит только объекты, созданные ЕГО
   СОБСТВЕННЫМИ биндингами. Зависимость через родительский скоуп
   закроет родитель.
— Отличие от get_it: там похожий метод называется `onDispose()`.
   Если переходите с get_it — первое место, где спотыкаются.
-->

# Подмена в тестах

```dart
class TestOverridesModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<ApiClient>().toInstance(MockApiClient());
  }
}

setUp(() {
  scope = CherryPick.openRootScope()
    ..installModules([AppModule(), TestOverridesModule()]);
});

tearDown(() => CherryPick.closeRootScope());
```

**Подмена — это ещё один модуль поверх боевых.** Тот же механизм, что в проде

<!--
Заметки спикера · 2 мин

— ПОРЯДОК ВАЖЕН: последний установленный биндинг того же типа
   перекрывает предыдущие. Модуль с подменами ставится ПОСЛЕ боевых.

   сборка графа устроена как боевая.

# Три рецепта, которые нужны всем

**Логаут — одной строкой**
```dart
await CherryPick.closeScope(scopeName: 'session');
```

**Две сессии одновременно** — два сабскоупа на одном уровне
```dart
root.openSubScope('session-a')..installModules([SessionModule(userA)]);
root.openSubScope('session-b')..installModules([SessionModule(userB)]);
```

**Экран-процесс** — скоуп на весь поток, не на экран: открыли на входе в оплату, закрыли на выходе, промежуточные экраны его переиспользуют

# Параметры времени выполнения

```dart
class OrderModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<OrderRepo>().toProvideWithParams(
      (params) => OrderRepo(id: params as String, api: currentScope.resolve<ApiClient>()),
    );
  }
}

final repo = scope.resolve<OrderRepo>(params: 'order-42');
```

**Зачем:** объект, которому нужен аргумент, известный только в рантайме — id заказа, номер счёта

> Это то, что в типизированных DI выражается тяжелее всего.
> Цена — `params` имеет тип `dynamic`


# Циклические зависимости

```dart
// Вариант 1: включить оба детектора для конкретного скоупа сразу
final scope = CherryPick.openGlobalSafeScope(scopeName: 'session');

// Вариант 2: включить раздельно
scope.enableCycleDetection();        // локальный (внутри скоупа)
scope.enableGlobalCycleDetection();  // кросс-скоуп (через границы)
```

**Два уровня:**
**Локальный** — цикл внутри скоупа: `scope.enableCycleDetection()` или `CherryPick.enableGlobalCycleDetection()` (для всех)

**Кросс-скоуп** — через границы: `scope.enableGlobalCycleDetection()` или `CherryPick.enableGlobalCrossScopeCycleDetection()` (для всех)

**Вместо стек-оверфлоу:** исключение с цепочкой `A → B → A`

<!--

# Кто закрывает скоуп экрана

```dart
class OrderScreenState extends State<OrderScreen> {
  late final Scope _scope;

  @override
  void initState() {
    super.initState();
    _scope = CherryPick.openScope(scopeName: 'session.order-${widget.id}')
      ..installModules([OrderModule(widget.id)]);
  }

  @override
  void dispose() {
    CherryPick.closeScope(scopeName: 'session.order-${widget.id}');
    super.dispose();
  }
}
```

**Или скоупом управляет роутер** — guard на входе в поток открывает, на выходе закрывает

<!--

# Чего не делать

**Не кладите всё в корневой скоуп.** Дерево вырождается в глобальный контейнер — время жизни снова «пока живёт процесс»

**Не резолвите в конструкторе модуля** — только внутри `builder`, иначе объект создастся при установке

**Не держите ссылку на закрытый скоуп.** После `closeSubScope` объект непригоден, берите по имени (`openScope` идемпотентен)

**Не ставьте `.singleton()` на параметрический биндинг** — закешируется первый параметр

**Не наследуйте `SilentCherryPickObserver`** — наблюдатель замолчит, нужен `implements`

# Резерв 3: «Зачем ещё один, если есть get_it?»

**`get_it` умеет, и это стоит знать точно:**

# Резерв 4: «А riverpod разве не решает всё это?»

**Решает — в своей модели.** `autoDispose`, `ref.onDispose`, `family`, `overrides`

**Разница в источнике времени жизни:** там оно **выводится** из подписок, здесь **объявляется**

Групповой сброс через `ProviderScope.clear()` закрыт как `wontfix`. Осознанная позиция, а не пробел

**Они не взаимоисключающие:** `riverpod` для состояния + скоупы для графа сервисов — рабочая комбинация

# Резерв 5: производительность

**Регистрация 1000 биндингов из 43 модулей — около 5,6 мс в AOT,** меньше 1% времени до первого кадра

**Бенчмарк** лежит в репозитории (`benchmark_di`), запускается одной командой

**Где get_it быстрее:** eager-синглтон (2,8 против 4,8 µs), override в дочернем скоупе

**Где cherrypick быстрее:** `AsyncChain` (247,8 против 15033 µs)

**Что думаю:** на типичном приложении DI не узкое место. Если стало — хочу увидеть этот кейс в issue

# Резерв 6: миграция 3.x → 4.0

**Четыре breaking-изменения, все механические:**

**1.** Удалены `Instance<T>` и `ProviderWithParams<T>` → используйте `ProviderFactory<T>` и `ProviderFactoryWithParams<T>`

**2.** `ProviderFactory<T>` теперь строго синхронный — асинхронное только через `toProvideAsync`

**3.** `toProvideAsync` принимает `Future<T>`, а не `FutureOr<T>`

**4.** `InstanceResolver` и `ProviderResolver` больше не экспортируются

**Изменение поведения:** async-синглтон после ошибки инициализации пробуется заново, а не кеширует ошибку

# Резерв 7: «Можно ли мигрировать постепенно с get_it?»

```dart
// легаси остаётся на get_it
GetIt.I.registerSingleton<LegacyService>(LegacyService());

// новая фича — на скоупах, с мостом в один биндинг
class NewFeatureModule extends Module {
  @override
  void builder(Scope currentScope) {
    bind<LegacyService>().toProvide(() => GetIt.I<LegacyService>());
    bind<NewRepo>().toProvide(() => NewRepo(currentScope.resolve<LegacyService>()));
  }
}
```

**Порядок:** новые фичи на скоупах → мост для легаси → сессионный скоуп → тесты → корень

Каждый шаг самодостаточен: можно остановиться на любом
