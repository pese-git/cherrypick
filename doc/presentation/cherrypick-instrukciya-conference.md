# Методичка к докладу «Binding, Module, Scope»

Инструкция для спикера к файлу `cherrypick-presentation-conference.md`.

---

## 1. Жанр и тональность

**Жанр:** инженерный рассказ «Я думал над этой задачей и вот что сделал».

Не сравнительный бенчмарк — первые три слайда дают контекст пространства решений,
а не рейтинг. Не рекламная питч-дека — библиотека не представляется как лучшая.
Не туториал — аудитория должна уйти с моделью, а не с выученными методами.

**Тональность:** ровная инженерная. Без самоуничижения («моя библиотека маленькая,
но…») и без гиперболы («единственное правильное решение»).

**Центральная мысль, которую слушатель должен унести:**
> Скоуп — это не папка для сервисов, а группа объектов с общей судьбой.
> Закрыли скоуп — ушли все.

Если эта мысль прошла — доклад удался, независимо от того, возьмут ли CherryPick.

## 4. Пять ключевых моментов

### 4.1 Пауза на первом слайде

Подзаголовок «Больше в CherryPick DI знать нечего» — это провокация, не факт.
Сделайте паузу после него в 2–3 секунды. Аудитория должна поднять бровь
или усмехнуться. Если реакции нет — скажите вслух: «Спойлер: кое-что ещё знать
придётся, но удивительно мало».

### 4.2 Слайд «Два вопроса» — карту показывают, не читают

Этот слайд объясняет **пространство**, а не оценивает игроков.
Покажите быстро: «Вот два вопроса, которые всё определяют. Ось одна — кто
решает когда умирать. Ось вторая — когда узнаёте об ошибке. CherryPick
вот здесь. Дальше объясню почему.» — и переходите. Не застревайте в объяснении
каждой позиции.

### 4.3 Слайд «Выбор: дерево скоупов» — читайте медленно

Три абзаца: задача, ограничение, решение. Это единственный слайд, где объясняется
**зачем** библиотека существует. Именно здесь называется цена — рантайм-резолвинг.
Назовите её нейтрально: «Я намеренно пошёл на это. Платим отсутствием ошибок
компилятора, получаем низкий барьер входа.»

### 4.4 Слайд «Зачем дерево» — пауза на диаграмме

Дерево скоупов — самый фотографируемый слайд. Дайте 10–15 секунд просто
посмотреть. Потом произнесите ключевую фразу: «Закрыли `session` — ушло всё
поддерево. Один вызов. Не нужно помнить список.»

### 4.5 Слайд «Три рецепта» — это момент «я могу это применить сегодня»

Логаут в одну строку — самый часто цитируемый кусок кода после докладов. Прочитайте
`await CherryPick.closeScope(scopeName: 'session')` вслух. Если успеваете —
спросите зал: «У кого логаут сейчас реализован так же просто?»

## 5. Ловушки API в слайдах

Знайте наизусть — вопросы по ним возникают сразу после показа кода.

### Ловушка 1: `toProvide` без `.singleton()` — не кешируется

Каждый `resolve` создаёт **новый экземпляр**. Слайд «Рабочий код» намеренно
показывает `.singleton()`, потому что для `ApiClient` это ожидаемое поведение.
Без него два разных места кода получат два разных клиента.

```dart
// ОК — один ApiClient на скоуп
bind<ApiClient>().toProvide(() => ApiClient()).singleton();

// ЛОВУШКА — каждый resolve = новый объект
bind<ApiClient>().toProvide(() => ApiClient());
```

### Ловушка 2: `SilentCherryPickObserver` — нельзя наследовать

```dart
// ЛОВУШКА — наблюдатель замолчит навсегда
class MyObserver extends SilentCherryPickObserver { ... }

// ВЕРНО
class MyObserver implements CherryPickObserver { ... }
```

Scope включает fast-path по `is SilentCherryPickObserver`. Наследник попадает
в него и не получает ни одного колбэка. Только `implements`.

### Ловушка 3: `toProvideAsync` — строго `Future<T>`

```dart
// ЛОВУШКА — не компилируется в toProvideAsync
bind<Db>().toProvideAsync(() => computeSyncDb());   // FutureOr<T>

// ВЕРНО — явный Future
bind<Db>().toProvideAsync(() async => Database.open('app.db'));
```

`toProvide` принимает `FutureOr<T>`. `toProvideAsync` — строго `Future<T>`.
Для асинхронных зависимостей всегда используйте `toProvideAsync`.

### Ловушка 4: `tryResolve` — null только при отсутствии биндинга

```dart
// tryResolve вернёт null ТОЛЬКО если биндинг не зарегистрирован
final a = scope.tryResolve<Analytics>();   // null — биндинга нет, всё ОК

// Незавершённый биндинг — это всё равно StateError, не null
```

`tryResolve` не «глотает» все ошибки. Зарегистрированный биндинг, упавший
при создании, бросит `StateError`.

### Ловушка 5: `.singleton()` на параметрическом биндинге

```dart
// ЛОВУШКА — кешируется первый параметр
bind<OrderRepo>().toProvideWithParams(
  (params) => OrderRepo(id: params as String, ...),
).singleton();

// первый вызов: resolve(params: 'order-42') → кеш OrderRepo(id: 'order-42')
// второй вызов: resolve(params: 'order-99') → вернёт тот же OrderRepo('order-42')
```

### Ловушка 6: `TestOverridesModule` должен идти после боевых

Побеждает последний биндинг одного типа. Порядок в `installModules` важен:

```dart
// ВЕРНО — тест перекрывает боевой
..installModules([AppModule(), TestOverridesModule()]);

// ЛОВУШКА — боевой перекрывает тест
..installModules([TestOverridesModule(), AppModule()]);
```

### Ловушка 7: `closeRootScope()` в tearDown обязателен

```dart
tearDown(() => CherryPick.closeRootScope());
```

Без этого тесты текут друг в друга через глобальное дерево. Паттерн «не закрыл
в tearDown → следующий тест видит объекты предыдущего» встречается стабильно
в первые дни работы с библиотекой.

### Ловушка 8: `openScope`/`closeScope` — `@experimental`

На слайде «Как открыть и закрыть» показаны оба стиля. `openScope` и `closeScope`
по пути `scopeName` помечены `@experimental`. Анализатор даёт три предупреждения
`experimental_member_use` — это норма для dev.4, не ошибки.

### Ловушка 9: именованные биндинги — неочевидный порядок

```dart
// Оба варианта эквивалентны (порядок withName/toProvide свободный)
bind<ApiClient>().withName('prod').toProvide(() => ApiClient('api.example.com'));
bind<ApiClient>().toProvide(() => ApiClient('api.example.com')).withName('prod');
```

Аудитория часто спрашивает, можно ли `withName` после `toProvide`. Можно.

### Ловушка 10: запутанная номенклатура детекторов циклов

| Метод | Что реально делает |
|---|---|
| `scope.enableCycleDetection()` | Локальный детект (внутри скоупа) |
| `scope.enableGlobalCycleDetection()` | **Кросс-скоуп** детект (через границы) |
| `CherryPick.enableGlobalCycleDetection()` | Локальный для **всех** скоупов |
| `CherryPick.enableGlobalCrossScopeCycleDetection()` | Кросс-скоуп для **всех** |

Называйте вслух: «`enableGlobalCycleDetection` на уровне CherryPick — локальный
для всех. Название запутано исторически.»

## 6. Типы аудитории

### Новичок в DI

Не знает, зачем DI вообще нужен. Задержитесь на слайде «Выбор: дерево скоупов»,
объясните устно задачу: «Представьте приложение с логином. Пока пользователь
вошёл — одни объекты. Вышел — они должны уйти. Кто это организует?»
Слайды 4–9 воспринимаются ими легче всего.

### Пользователь get_it

Знает DI, привык к `GetIt.I.get<T>()`. Его вопрос: «Зачем переусложнять?»
Ответ прямо в слайде «Зачем дерево»: два заказа одновременно в линейном стеке
невозможны без хаков. Скоуп — это не усложнение, это способ выразить
параллельные ветки жизни.

### Пользователь riverpod

Знает состояния и провайдеры. Для него ключевая разница: в riverpod время жизни
определяется деревом виджетов или явным `.autoDispose`. В CherryPick — явным
деревом скоупов, не связанным с виджетами. Это позволяет управлять жизнью
бизнес-объектов независимо от UI.

### Архитектор монорепозитория

Интересуется организацией в масштабе. Слайды «Модуль — это объект» и «Граф из
пакетов» (расширение) — его слайды. Ключевая мысль: пакет отдаёт `Module`, не знает
о приложении. Состав фичи виден одним объектом.

### Скептик

Начнёт с «Почему не использовать X?». Не спорьте — признайте сразу:
«Это нишевое решение. Если вас устраивают гарантии компилятора — возьмите yx_scope.
Если хотите низкий барьер входа и гибкость времени жизни — посмотрите на это.»
Слайд «Цена выбора» (расширение) специально для него.

## 7. Q&A: подготовленные ответы

### «Почему рантайм, а не компиляция?»

«Сознательный обмен: рантайм проще для освоения, ниже барьер входа.
Платим тем, что забытый биндинг даёт ошибку при запуске, не при компиляции.
На практике это покрывается тестами и детектором циклов в debug-сборке.»

### «Один мейнтейнер — это не страшно?»

«Apache 2.0 — форкается без разрешения. Если проект бросить, библиотека
остаётся в своём последнем состоянии и продолжает работать. Зависимость
от одного мейнтейнера — честный риск, который стоит учитывать при выборе.»

### «Чем отличаетесь от yx_scope?»

Достаньте резервный слайд Р1. Коротко: «Оба — дерево скоупов. yx_scope даёт
ошибки при компиляции через типизированные поля, CherryPick — рантайм-резолвинг
с меньшим числом концепций. Разные обмены, одна задача.»

### «У get_it тоже есть scopes, зачем переходить?»

«В get_it scope — это стек: открыл, поработал, закрыл. Два scope одновременно
на одном уровне дерева (два активных заказа, два аккаунта) — это хак через
два отдельных GetIt-инстанса. В CherryPick сиблинги — первоклассный сценарий.»

### «Насколько быстро?»

Достаньте резервный слайд «Производительность»: «5,6 мс на 1000 биндингов в AOT —
меньше 1% от 608 мс до первого кадра. Бенчмарк в репо, повторяется.»

### «Можно ли мигрировать с get_it не всё сразу?»

Достаньте резервный слайд «Постепенная миграция». Коротко: «Оберните старый
`GetIt.I.get<T>()` в биндинг-мост. Новые фичи — на скоупах. Мигрируйте слой
за слоем. Каждый шаг самодостаточен.»

### «Какая версия стабильна?»

«4.0.0-dev.4 — предрелиз, который мы используем в проде. `dev` здесь —
версионная метка, а не признак нестабильности: API устоялось, breaking-изменений
до 4.0.0 не планируется. Если важен стабильный тег — ждите 4.0.0.»

### «Как отлаживать, если что-то не резолвится?»

«Три инструмента: `CherryPick.getCurrentResolutionChain()` покажет,
где цепочка обрывается; наблюдатель (`CherryPickObserver`) — все события;
`enableCycleDetection()` в debug-сборке — циклы.»

## Приложение: вступительный крючок

Первые 30–60 секунд речи. Три варианта с разным характером входа — выбирайте
под ощущение от зала.

### Вариант 1 — через боль аудитории

*Работает на любой аудитории. Поднятые руки создают контакт с залом.*

> «Поднимите руку, у кого логаут когда-нибудь протекал.
> То есть — нажали выйти, а потом обнаружили, что объекты
> прошлой сессии где-то всё ещё живут.
>
> *(Пауза. Смотрите на руки.)*
>
> Хорошо. Держите руки — ещё один вопрос.
> У кого это случилось больше одного раза?
>
> *(Пауза.)*
>
> Вот именно. Сегодня я расскажу, почему это повторяется —
> и покажу, как логаут становится одной строкой кода.»

### Вариант 2 — через провокацию заголовка

*Работает, если хочется сразу взять тон "уверенный, но самоироничный". Пауза обязательна.*

> «Binding, Module, Scope. Больше знать нечего.
>
> *(Пауза 3 секунды. Дайте залу прочитать и отреагировать.)*
>
> Ну, почти. Кое-что знать ещё придётся — но удивительно мало.
>
> За следующие тридцать минут я покажу три понятия,
> после которых логаут — это одна строка,
> два аккаунта одновременно — не архитектурная проблема,
> и тесты перестают течь друг в друга.
>
> Начнём с того, почему вообще нужен ещё один DI-фреймворк.»

### Вариант 3 — через парадокс

*Работает на технически сильной аудитории. Интеллектуальный вход без вопросов к залу.*

> «DI обычно обсуждают через создание.
> Как создать объект. Как передать зависимость.
>
> У меня был другой вопрос: кто решает, когда объект умрёт?
>
> *(Пауза.)*
>
> В большинстве приложений ответ — никто конкретный.
> Процесс завершился — всё ушло.
> Или объект живёт, пока виджет на экране.
> Или вы вручную вызываете unregister и надеетесь, что не забыли.
>
> Я захотел, чтобы на этот вопрос был чёткий структурный ответ.
> Вот что из этого вышло.»

### Как выбрать

| Ситуация | Вариант |
|---|---|
| Незнакомый зал, разношёрстная аудитория | 1 — руки вверх снимают напряжение |
| Зал уже «тёплый», есть атмосфера | 2 — игра с заголовком |
| Митап с сильными разработчиками, академичный тон | 3 — парадокс |
